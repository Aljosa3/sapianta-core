# SAPIANTA — Phase v0.11 DIRECTORY & MODULE MAP
## Passive Observability Implementation (Repository Placement)

Status: DIRECTORY-MAP
Phase: v0.11
Depends On:
- v0.11_INIT
- v0.11_IMPLEMENTATION_OUTLINE
Introduces Code: NO
Introduces Behavior: NO

---

## 1. Purpose

This document defines the **canonical repository placement** of all
Phase v0.11 implementation components.

It specifies:
- directory boundaries,
- module responsibilities by location,
- isolation rules between layers,

and explicitly does **not** specify:
- implementation details,
- internal APIs,
- logic or control flow.

---

## 2. Canonical Placement Principles

All v0.11 observability components MUST:

- be isolated from runtime execution logic,
- be isolated from guard lifecycle logic,
- be removable without breaking execution,
- depend only on declared runtime interfaces.

No observability module may:
- import runtime control code,
- import guard decision logic,
- expose control surfaces.

---

## 3. Top-Level Directory Allocation

All Phase v0.11 implementation code SHALL reside under:
/runtime/observability/


This directory is defined as:
- passive
- non-authoritative
- non-executing

---

## 4. Module-Level Structure (Closed Set)

The `/runtime/observability/` directory SHALL contain the following modules:
runtime/
└── observability/
    ├── __init__.py
    ├── events/
    ├── snapshots/
    ├── context/
    ├── guard_outcomes/
    ├── audit/
    ├── registry/
    └── config/


No additional top-level modules are permitted in v0.11.

---

## 5. Module Responsibilities (By Directory)

### 5.1 events/
Responsible for:
- Execution Event Recorder implementation

Must not:
- interpret event meaning
- aggregate or filter events

---

### 5.2 snapshots/
Responsible for:
- Execution State Snapshot Recorder implementation

Must not:
- compare snapshots
- infer transitions
- support rollback

---

### 5.3 context/
Responsible for:
- Execution Context Binder implementation

Must not:
- validate context
- influence execution behavior

---

### 5.4 guard_outcomes/
Responsible for:
- Guard Outcome Recorder implementation

Must not:
- trigger guards
- evaluate guard results

---

### 5.5 audit/
Responsible for:
- Audit Enrichment Writer implementation

Must not:
- modify existing audit records
- summarize or classify audit data

---

### 5.6 registry/
Responsible for:
- Introspection Artifact Registry implementation

Must not:
- rank or prioritize artifacts
- expose decision interfaces

---

### 5.7 config/
Responsible for:
- Observability Configuration Surface implementation

Must not:
- allow runtime mutation
- introduce dynamic toggling logic

---

## 6. Boundary Enforcement

The following directory-level dependencies are explicitly forbidden:

- observability → runtime control logic
- observability → guard lifecycle logic
- observability → orchestration layers
- observability → LLM interfaces

Allowed dependencies are **read-only interfaces only**.

---

## 7. Completion Criteria

This directory map is considered complete when:

- each v0.11 component has exactly one placement,
- no directory implies behavior or control,
- structure fully matches v0.11 implementation outline.

---

## 8. Canonical Closure

This document defines the **exclusive directory and module layout**
for Phase v0.11.

Any structural change requires an explicit revision of v0.11 INIT.

END OF DOCUMENT
