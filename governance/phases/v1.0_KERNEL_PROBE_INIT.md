# v1.0 — KERNEL PROBE INIT
Status: INIT
Scope: Kernel validation through real usage
Mode: Read-only, non-adaptive
Depends-On: v0.11 (Kernel Readiness), v0.20 (Kernel Boundary Lock)

---

## 1. PURPOSE

The purpose of the v1.0 KERNEL PROBE is to validate whether the locked kernel
(v0.20) is practically usable for real modules **without adding any new
capabilities**.

This is not a product, agent, or intelligent system.
It is an **instrumented usage probe**.

---

## 2. WHAT THIS MODULE IS

The Kernel Probe module is:

- a real module using the kernel
- executing decisions through the full guard lifecycle
- fully observable and auditable
- constrained to kernel-native functionality

It exists solely to answer the question:

> “Can meaningful, explainable, and controlled behavior be built on the current kernel?”

---

## 3. WHAT THIS MODULE IS NOT

The Kernel Probe module MUST NOT:

- learn from past executions
- adapt its behavior over time
- store long-term memory
- modify kernel rules or policies
- introduce new capabilities (v0.12–v0.19)

Any attempt to do so is considered **scope violation**.

---

## 4. SUCCESS CRITERIA

The Kernel Probe is considered successful if it can demonstrate:

1. Clear and usable **decision boundaries**
2. Predictable and non-obstructive **guard lifecycle behavior**
3. Human-understandable **explanations of outcomes**
4. Sufficient **observability signals** to diagnose problems
5. No immediate pressure to introduce learning or memory

Success does NOT mean correctness of answers.
Success means **clarity, control, and debuggability**.

---

## 5. FAILURE SIGNALS (INPUT FOR FUTURE CAPABILITIES)

The following are considered valid outcomes:

- repetitive decisions with no improvement
- excessive guard friction
- lack of contextual continuity
- weak or confusing explanations

These are NOT failures of the probe.
They are **signals** for possible future capabilities.

---

## 6. RELATION TO CAPABILITY DOMAINS

This module does not implement any Capability Domain.

However, it may generate **justified signals** pointing toward:

- POLICY_ADAPTATION
- MEMORY
- LEARNING
- DRIFT_CONTROL

Only after sufficient signal accumulation may a capability be considered.

---

## 7. LOCK POLICY

This INIT document defines the entry into usage-driven development.

No lock is applied at this stage.

Any capability introduced as a reaction to probe signals
must be documented and locked **locally**, without modifying the kernel.

---

## 8. EXIT CONDITION

The Kernel Probe phase exits when:

- at least one real usage scenario has been exercised
- signals have been reviewed and classified
- a conscious decision is made to either:
  - continue with kernel-only usage
  - introduce a specific, minimal capability

At exit, this document may be marked COMPLETE.

---

End of document.
