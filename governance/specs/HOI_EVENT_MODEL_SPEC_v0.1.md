# HOI_EVENT_MODEL_SPEC_v0.1
Status: LOCK 
Layer: HOI Execution Layer  
Scope: Deterministic Event Model  
Compatibility:
- HOI_CANONICAL_STATE_OBJECT_SPEC_v0.1
- HOI_STATE_MACHINE_SPEC_v0.1

---

## 1. PURPOSE

This document defines the deterministic event model that drives
the HOI execution state machine.

It formalizes:

- Enumerated event types
- Event structure
- Event immutability
- Event → transition binding
- Event validity constraints
- Append-only event logging rules

This specification defines the complete input domain of the HOI state machine.

No LLM logic.
No advisory logic.
No adaptive behavior.

Execution-layer only.

---

## 2. EVENT MODEL PRINCIPLES

The event model MUST satisfy:

- Determinism
- Finite enumerability
- Serializability
- Immutability
- Explicit origin
- Explicit type
- Explicit intent

No implicit events allowed.
No inferred events allowed.
No synthetic auto-events allowed.

---

## 3. EVENT ENUMERATION

Only the following event types are valid:

1. START
2. PAUSE
3. RESUME
4. COMPLETE
5. TERMINATE
6. ILLEGAL_TRANSITION_ATTEMPT

No additional event types are permitted.

---

## 4. EVENT → STATE TRANSITION BINDING

Each event maps deterministically to a legal state transition.

| Event       | Allowed Current State | Target State |
|------------|----------------------|--------------|
| START      | INIT                 | ACTIVE       |
| PAUSE      | ACTIVE               | PAUSED       |
| RESUME     | PAUSED               | ACTIVE       |
| COMPLETE   | ACTIVE               | COMPLETED    |
| TERMINATE  | ACTIVE, PAUSED       | TERMINATED   |

If event does not match allowed current state,
the transition MUST be rejected and handled as illegal.

---

## 5. EVENT STRUCTURE

Each event MUST contain:

- event_type (enum)
- source (string identifier)
- timestamp (external system-provided)
- correlation_id (optional but immutable)
- metadata (optional, immutable key-value map)

Events MUST be fully serializable.

No dynamic function pointers.
No closures.
No embedded executable logic.

---

## 6. EVENT IMMUTABILITY

Once created:

- Event fields MUST NOT be mutated.
- Event payload MUST NOT be modified.
- Event objects are read-only.

If modification required → new event instance must be created.

---

## 7. EVENT VALIDATION RULES

Before applying event to state machine:

1. event_type MUST be valid enumeration
2. current_state MUST be compatible
3. state MUST NOT be terminal (unless TERMINATE is already final)
4. event MUST pass deterministic transition table

Failure triggers:

- ILLEGAL_TRANSITION_ATTEMPT event
- State remains unchanged

---

## 8. ILLEGAL_TRANSITION_ATTEMPT EVENT

This event is generated by execution layer when:

- Event type is invalid
- Event-state mismatch occurs
- Transition violates terminal rule
- Guard conditions fail

This event:

- MUST be appended to lifecycle.history
- MUST NOT change lifecycle.current_stage

It is internal and deterministic.

---

## 9. EVENT SOURCE

Event source MUST be explicit and deterministic.

Examples:

- "cli"
- "system"
- "api"
- "scheduler"

Execution layer MUST NOT infer source.

No anonymous events allowed.

---

## 10. RELATIONSHIP TO CANONICAL STATE OBJECT

Events:

- Drive lifecycle.current_stage transitions
- Produce append-only entries in lifecycle.history
- MUST NOT mutate other canonical state sections

State machine consumes events.
State object records outcome.

---

## 11. APPEND-ONLY EVENT RECORDING

For every processed event:

1. Original event MUST be recorded
2. Resulting state transition (if legal) MUST be recorded
3. If illegal → illegal event entry MUST be recorded
4. No deletion
5. No mutation
6. No compression

History is strictly append-only.

---

## 12. DETERMINISTIC EXECUTION CONTRACT

State transitions are defined as:

NextState = f(CurrentState, Event)

Where:

- f is fully determined by:
  - HOI_STATE_MACHINE_SPEC_v0.1
  - This event specification
- No stochastic behavior
- No learning
- No advisory override

---

## 13. EXCLUDED CONCERNS

This specification does NOT include:

- Advisory evaluation
- Guard-layer logic changes
- Business rules
- Runtime optimization
- Multi-agent coordination
- Policy injection

Execution layer only.
