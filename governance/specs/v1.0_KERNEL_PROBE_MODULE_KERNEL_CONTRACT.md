# v1.0 — MODULE ↔ KERNEL CONTRACT
## KERNEL_INTROSPECTION_PROBE

Status: SPEC (Draft → Lock after first successful probe run)
Scope: Contract between module and kernel
Mode: Read-only, non-adaptive
Kernel-State: BOUNDARY_LOCK (v0.20)

---

## 1. PURPOSE

This document defines the **strict interface and behavioral contract**
between a probe module and the locked kernel.

The contract exists to ensure:
- clear decision boundaries
- full guard lifecycle enforcement
- stable observability/audit surfaces
- prevention of hidden capability emulation (memory/learning/adaptation)

---

## 2. ROLES

### 2.1 Module responsibilities
The module is a **client** of the kernel. It must:
- submit decision requests
- present kernel outputs to the caller
- never modify kernel rules or state
- never persist cross-invocation state (no memory)

### 2.2 Kernel responsibilities
The kernel is an **authority**. It must:
- evaluate decisions through guard lifecycle
- produce explainable outcomes
- emit auditable/observable traces
- enforce constraints deterministically

---

## 3. CONTRACT INVARIANTS (NON-NEGOTIABLE)

I1 — Stateless Invocation  
Each request is evaluated as an independent event. No cross-request state is allowed.

I2 — Guard Lifecycle Mandatory  
Every decision must pass through guard evaluation. No bypass is permitted.

I3 — Explainability Required  
Every decision must include a minimal explanation surface.

I4 — Observability Required  
Every decision must produce trace identifiers and event records.

I5 — No Implicit Capability Emulation  
The module must not simulate memory/learning/adaptation via caching, heuristics, or hidden storage.

Violation of any invariant is a **contract breach**.

---

## 4. API SHAPE (LOGICAL INTERFACE)

### 4.1 DecisionRequest (module → kernel)
The module MUST send a request with the following logical fields:

- request_id: string (unique per invocation)
- actor: string (module identity)
- user_input: string (raw user prompt)
- declared_intent: string | null (optional)
- risk_level: low | medium | high | unknown
- constraints: object (optional explicit constraints)
- context: object (optional, non-persistent)

Notes:
- context MUST be treated as ephemeral.
- the module MUST NOT add history or previous outputs.

### 4.2 DecisionResponse (kernel → module)
The kernel MUST return:

- request_id: string
- outcome: allow | deny | constrain | defer
- confidence: low | medium | high
- constraints_applied: object | null
- explanation:
  - summary: string
  - key_factors: [string]
- guards:
  - triggered: [string] (guard ids)
  - notes: string | null
- observability:
  - trace_id: string
  - timestamp: ISO-8601
  - event_ids: [string] | null

---

## 5. OUTCOME SEMANTICS

### allow
- The module may proceed to present/execute the requested action/output
- No additional constraints required beyond normal kernel constraints

### deny
- The module must refuse the action/output
- Explanation must clearly state the primary factors

### constrain
- The kernel provides constraints_applied
- The module must obey constraints exactly and present them explicitly

### defer
- The module must ask for additional input OR route to a safe fallback
- Defer must include explanation of missing prerequisites

---

## 6. GUARD LIFECYCLE REQUIREMENTS

G1 — Guard evaluation MUST be recorded  
The kernel must produce an auditable record that includes:
- guard identifiers triggered
- pass/soft-block/hard-block outcome (or equivalent)
- minimal notes or reason codes

G2 — Guard outcomes MUST map to final outcome  
- deny MUST have at least one hard-blocking guard or equivalent reason
- constrain MUST have at least one constraining guard or equivalent reason
- allow MUST not contain any unresolved block outcome

G3 — No silent guard behavior  
If guard affected the outcome, it must appear in response.guards.triggered.

---

## 7. OBSERVABILITY / AUDIT SURFACE

O1 — trace_id is mandatory  
Every response must include trace_id.

O2 — timestamp is mandatory  
Every response must include timestamp.

O3 — event binding  
The kernel must bind the decision to observable events such that:
- later reconstruction of “what happened” is possible
- the module can reference trace_id in logs and reports

O4 — Module logging constraints  
The module may log:
- request_id, trace_id, outcome, triggered guards list
The module must not log sensitive raw content if prohibited by policy (handled by kernel policy).

---

## 8. PROHIBITED MODULE PATTERNS (STRICT)

The module MUST NOT:
- persist prior user_input, decisions, explanations, constraints, or trace outputs
- cache kernel responses for reuse
- implement “helpful heuristics” that override kernel outcomes
- auto-relax constraints or reframe denied tasks into allowed tasks without explicit kernel re-evaluation
- add hidden memory via local files, databases, or environment state

Any of the above is considered **implicit capability emulation**.

---

## 9. ACCEPTABLE MODULE PATTERNS

The module MAY:
- validate schema of inputs/outputs
- present kernel output in a structured user-facing format
- request additional user input when outcome=defer
- run the same request again ONLY as a new request_id (fresh evaluation)

---

## 10. CHANGE CONTROL

Any change to:
- outcome semantics
- required response fields
- guard lifecycle mapping
- observability requirements

is considered a **kernel contract change** and requires:
- a new spec revision
- explicit approval under kernel governance
- (if kernel behavior changes) a new kernel governance milestone (v0.21+)
