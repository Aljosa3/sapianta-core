# SAPIANTA — v0.9 EXECUTION SEMANTICS SPEC
## Status: DRAFT (Phase v0.9)

## Purpose
This specification defines **execution semantics** within the SAPIANTA runtime.
Execution semantics assign *meaning* to execution events **without introducing intent,
decision-making, interpretation, or behavioral change**.

This document answers:
- What semantic meaning may be attached to an execution?
- Who assigns this meaning?
- How is this meaning represented and propagated?
- What are the absolute limits of semantic influence?

## Normative Context
This specification operates strictly under:
- SCF v0.3 (Canonical Authoring)
- SCF v0.4 (Execution Boundary & Guard Lifecycle)
- v0.6 Canonical Passive Runtime Layer
- v0.7 Structural Runtime Wiring
- v0.8 Controlled Runtime Execution

No rule in this document may override or reinterpret the above.

## Core Invariant
> **Execution semantics describe what an execution *is*, never what it *does*.**

Semantics are **descriptive metadata**, not control logic.

## Definition: Execution Semantics
Execution Semantics are **finite, Guard-assigned semantic labels** attached to an
execution event.

They:
- carry no executable logic
- influence no control flow
- trigger no side effects
- authorize no actions
- mutate no state beyond metadata

## Semantic Authority
- **Guard Lifecycle** is the sole authority that assigns execution semantics.
- Runtime MUST NOT:
  - infer semantics
  - alter semantics
  - select semantics
  - branch on semantics

## Canonical Semantic Set (v0.9)

The following semantic types are **exhaustive for v0.9**.

### 1. NO_OP
Indicates an execution that has no declared effect.
- Used for structural or placeholder execution
- Carries no implied consequence

### 2. AUDIT_ONLY
Execution exists solely for audit traceability.
- No effect beyond recording
- No implied outcome

### 3. DECLARED_EFFECT
Execution represents an externally declared effect.
- The effect is **descriptive only**
- Runtime does not enact or verify the effect

### 4. DRY_RUN_EFFECT
Execution represents a simulated or hypothetical effect.
- No real-world consequence
- Used for inspection, preview, or validation contexts

No other semantic values are permitted in v0.9.

## Semantic Attachment Rules
- Semantics SHALL be attached at execution event creation time.
- Semantics SHALL be immutable for the lifetime of the event.
- Semantics SHALL be preserved verbatim through runtime propagation.
- Semantics SHALL be included in audit records.

## Prohibited Uses
Execution semantics MUST NOT:
- determine execution order
- enable or disable execution
- alter runtime wiring
- influence orchestration
- substitute Guard decisions
- encode intent, confidence, or probability
- carry instructions

Any such use constitutes a **phase boundary violation**.

## Audit Integration
Each execution event SHALL expose its semantic label to the audit layer.

Audit records MUST:
- record the semantic value
- record the assigning Guard context
- preserve semantic integrity

Audit MUST NOT reinterpret or summarize semantics.

## Forward Compatibility
- Extension of the semantic set is **forbidden in v0.9**.
- Any new semantic category requires:
  - a new phase INIT
  - an explicit boundary specification
  - a LOCK prior to usage

## Exit Criteria (for v0.9)
This specification is considered complete when:
- Semantic types are finalized and locked
- No runtime behavior depends on semantics
- Audit visibility is confirmed
- No additional semantic categories are proposed

## Phase Guarantee
Upon completion of v0.9:
- Execution has meaning
- Meaning has no power
- Power remains exclusively with Guard
